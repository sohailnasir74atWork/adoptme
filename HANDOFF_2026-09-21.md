# Handoff — 2026-09-21

React Native 0.83.10, the iOS silent-logout fix, and startup instrumentation.
Shipped as **1.15.38 (164)** on Android; iOS still needs an Xcode archive.

Read the "What was NOT fixed" section before planning follow-up work. Several
confident diagnoses made during this session were disproven by testing, and the
record of what failed is more useful than the record of what changed.

## 1. React Native 0.83.4 → 0.83.10

Patch-level bump on the same minor. **No native files needed changes** — verified
against the official upgrade diff, not assumed:

    https://react-native-community.github.io/upgrade-helper/?from=0.83.4&to=0.83.10

That diff touches exactly one file, `package.json`, and it bumps **six**
packages. `npm install react-native@0.83.10` only does one of them. The other
four must be bumped by hand or you ship a JS bundle transpiled by the old
babel-preset against the new runtime:

    @react-native/babel-preset
    @react-native/eslint-config
    @react-native/metro-config
    @react-native/typescript-config

`@react-native-community/cli` stays at 19.0.0 — the template's 20.0.0 is its own
choice, unchanged across this range.

Fixes in 0.83.5–0.83.10 that land on code this app actually uses:

- **`removeClippedSubviews` crash** — 15 call sites across HomeScreen, Trades,
  ValueScreen and every chat list.
- **Hermes crash** when an async void TurboModule method throws NSException.
- **Appearance** colour scheme wrong after being set to `unspecified`.
- **`fetch()`** returning the pre-redirect URL; `file://` URIs failing.
- **`fmt` 11.0.2 → 12.1.0** (Xcode 26.4 fix). This one forces `RCT-Folly` along
  with it and is why a plain `pod install` fails — see section 4.

Verified: clean `assembleRelease` in 22m13s, all four ABIs, JS bundle embedded.
APK grew 184 KB (0.4%).

## 2. iOS silent logout — Firebase iOS SDK pinned to 12.19.0

**The single best-evidenced fix in this session.** Crashlytics issue `98edaf64`:
`auth_signed_out reason=native-null`, **256 events / 100 users a week**, and 94%
of all iOS Crashlytics events on 11.5.

Firebase iOS 12.19.0 changelog (#16498):

> Fixed an issue on iOS 15+ where users were randomly logged out during
> prewarming while the device was locked.

Mechanism: iOS prewarms the app process before the user taps the icon, often
while the device is locked. The keychain is unreadable when locked, so Auth
cannot restore the persisted session and reports a null user. Our telemetry
records `msSinceLaunch` around 100ms, which is a prewarmed launch, not a
user-initiated one.

Every precondition was checked: deployment target is iOS 15.1, and 100% of
affected devices were iOS 26.2–27.0.

**Upgrading React Native Firebase does not fix this.** RNFB 23.8.8 resolves
Firebase iOS 12.10.0; even the current RNFB 26.4.0 ships only 12.18.0. The pin
is mandatory — `ios/Podfile`:

    $FirebaseSDKVersion = '12.19.0'

Use **12.19.0 exactly**. 12.19.1 and 12.19.2 exist on GitHub but were never
published to the CocoaPods trunk, and CocoaPods misreports that as a
"higher minimum deployment target" error, which sends you chasing the wrong
problem.

This mirrors the Android BoM 34.18.0 pin already in `android/build.gradle`. The
Android fix (firebase-auth 24.2.0, 2026-09-04, 1.15.26) was a **Gradle** pin and
therefore never applied to iOS — which is why iOS was still broken five months
later while Android recovered.

### Did the Android fix work?

Yes, apparently. On 1.15.37 the only auth non-fatal left is
`auth_login_reads_unreachable` (40 events / 16 users); the `native-null`
signature is absent from 1.15.34 and 1.15.37.

"Apparently" because **there is no baseline**. The telemetry shipped in the same
commit as the fix, so every earlier version reports zero — not because the bug
was absent but because nothing was watching. Do not repeat this: ship
instrumentation *before* the fix it is meant to evaluate.

For iOS the baseline now exists: **256 events / 100 users on 11.5, week of
2026-09-14**. Re-run the same query one week after the iOS build ships.

## 3. Startup instrumentation (new)

Three signals added so the next investigation starts from data.

### `installer` — Crashlytics custom key

`MainApplication.kt`, set on the existing `tagTamperedDevice()` background
thread, so it costs nothing at startup.

Exists to settle Crashlytics `74c5924b` (SoLoader "couldn't find DSO to load",
357 crashes / 50 users, 100% in the first second). `com.android.vending` means a
real Play install and the crash is ours; anything else — or `none`, the classic
sideload signature — means it is not. **Right now those two worlds are
indistinguishable in the crash report, and they demand opposite responses.**

### `startup_ready` and `startup_profile_reads` — Firebase Analytics

`Code/GlobelStats.js`, via a `logStartupTiming` helper.

**These go to Analytics, not only Crashlytics, and that matters.**
`crashlyticsLog` writes a breadcrumb visible *only if that session later
crashes* — the worst possible sample for "how long does startup take." Analytics
aggregates across all users. The Crashlytics breadcrumb is kept too, because
knowing startup took 9s before a crash is useful context.

- `startup_ready { ms }` — process start to splash hide. **True
  time-to-interactive.** `am start -W` does not measure this; it stops at first
  draw, which is only the splash appearing.
- `startup_profile_reads { ms, supabase_ok, rtdb_ok, rtdb_total }` — the 13
  network calls that gate the splash, plus how many actually succeeded. A low
  `rtdb_ok` is the same backend-reachability problem that
  `auth_login_reads_unreachable` has been hinting at.

Read them together: they split startup into "the network" versus everything
else. If `startup_ready` has a flat median and a long p95 tail, caching the user
profile in MMKV is worth building. If the distribution is flat, warm-up was
never the problem.

`@react-native-firebase/analytics` was already installed (23.8.8) and entirely
unused, so no new native modules and no pod changes were needed here.

### Crashlytics native symbols — a silent bug, now fixed

`android/app/build.gradle` had `nativeSymbolUploadEnabled true` with
`unstrippedNativeLibsDir` pointing at the **pre-AGP-8** intermediates layout:

    build/intermediates/merged_native_libs/release/out/lib          # does not exist
    build/intermediates/merged_native_libs/release/mergeReleaseNativeLibs/out/lib   # correct

The Crashlytics plugin does not fail on a missing directory. It uploads nothing,
forever. That is why issue `85c581ed` (`[libc.so]`, SIGABRT, 52 crashes / 41
users a week) arrives with ten bare `at` frames and nothing else.

**Two things to know:**

1. The path is AGP-version-sensitive and will break silently again on an AGP
   bump. After bumping AGP, `ls` the directory before trusting a native stack.
2. **`uploadCrashlyticsSymbolFileRelease` is NOT wired into `bundleRelease`.**
   It never ran in any build this session until invoked explicitly. Fixing the
   path was necessary and not sufficient — run it for every shipped build:

       ./gradlew :app:bundleRelease
       ./gradlew :app:uploadCrashlyticsSymbolFileRelease

## 4. iOS pods — what actually works

`pod install` alone fails on this upgrade. Locked versions block the new
podspecs, and CocoaPods reports it confusingly. Sequence that works:

    cd ios
    export LANG=en_US.UTF-8 LC_ALL=en_US.UTF-8   # CocoaPods crashes in
                                                 # unicode_normalize without a locale
    # RN's third-party pods must move together (fmt forces RCT-Folly)
    pod update fmt RCT-Folly boost glog DoubleConversion SocketRocket \
               hermes-engine Yoga fast_float

**If Firebase AND React Native both change, update them in ONE `pod update`.**
Splitting it deadlocks: the RN-pods step fails on the pending Firebase pin, and
the Firebase step fails because `fmt` changed locally — each blocked by the
other's uncommitted change. This did not happen in adoptme-jan7 only because
Firebase was pinned *before* the RN bump, so each run faced one moving family.
Blox_Fruit hit it immediately. The fix is a single invocation listing both sets:

    xargs pod update < allpods.txt   # RN third-party pods + every Firebase* pod

**Do not delete `Podfile.lock`.** `GoogleMobileAdsMediationFacebook` and
`GoogleMobileAdsMediationUnity` are declared with no version constraint, so a
fresh resolve silently bumps your ad SDK. That is a revenue-affecting change and
does not belong in an RN patch bump.

Firebase pods were moved separately, with every `Firebase*` pod in the lock
passed to a single `pod update` — bumping them piecemeal fails one transitive
dependency at a time (`FirebaseCoreExtension`, `FirebaseSessions`, …).

Verified after: `Podfile.lock` ≡ `Pods/Manifest.lock`, `React-Core` 0.83.10,
`FirebaseAuth` 12.19.0, `fmt` 12.1.0.

### Two warnings worth tracking

- **Firebase is leaving CocoaPods.** "New versions will no longer be published
  to CocoaPods after October 2026." That is why 12.19.1/12.19.2 are missing. A
  Swift Package Manager migration is on the horizon — plan it rather than
  discover it.
- **`EXCLUDED_ARCHS` conflict** between `FBAudienceNetwork` and
  `IronSourceAdQualitySDK`. Pre-existing. Typically breaks simulator builds on
  Apple Silicon while device builds are fine.

### iOS crash symbols are fine

The `[CP-User] [RNFB] Crashlytics Configuration` build phase runs
`${PODS_ROOT}/FirebaseCrashlytics/run`, which uploads dSYMs automatically —
confirmed by iOS crashes arriving with real file and line numbers. The
"no symbol file" prompt at App Store upload is **Apple's** separate symbol
system, feeding Xcode Organizer, not Crashlytics. Safe to ignore; enabling it
just gives you a second view.

## 5. What was NOT fixed

Be honest about this when planning the next session.

**Crash #1 — SoLoader launch crash (357 events / 50 users): still undiagnosed.**
The `x86_64` `abiFilters` change was **proven a no-op** by building the AAB both
ways — both contained all four ABIs, 26 libs each. `ndk.abiFilters` only filters
NDK-built code; it does **not** filter prebuilt `.so` files inside AAR
dependencies, which in an RN app is all of them. What actually controls shipped
ABIs is `packaging { jniLibs { excludes } }`. The change was reverted.

The live lead: the crash log shows `DirectApkSoSource` listing language and
density splits (`split_config.ja.apk`, `split_config.tvdpi.apk`) all resolving
to `!/lib/arm64-v8a`, which is not how Play delivers splits. That suggests
sideloaded or repackaged split-APK sets on x86_64 emulators. The new `installer`
key settles it.

**Crash #2 — `[libc.so]` SIGABRT (52 / 41): still undiagnosed**, but readable
from 164 onward now that symbols upload.

**ANRs (`nativePollOnce` 43 / 41): still unexplained.** One suspect eliminated:
a release build showed **zero `Choreographer` skipped frames** across a full
25-second launch, and `MainApplication.onCreate` is already lean. The main
thread is not blocked during startup, so that is not the cause.

**"Slow warm-up" was not reproducible.** Release cold start is **235 ms median**
(6 runs). Earlier figures of 1209 ms and 3519 ms were debug-build and
loaded-host artifacts. Memory likewise: 505 MB PSS / 262 MB native heap in debug
collapsed to **284 MB / 55 MB** in release, which is unremarkable — an
image-caching recommendation built on the debug number was withdrawn.

The one place warm-up might still be real is time-to-interactive, which was
never measured. That is exactly what `startup_ready` now answers.

## 6. Applying this to the sibling apps

`Blox_Fruit` and `mm2values` are forks of this codebase. See
`repo-to-app-mapping` — folder names do not match the shipped apps.

### mm2values has no Analytics on iOS at all

**Confirmed 2026-09-21.** `@react-native-firebase/analytics` is not a dependency
there. Android still reports because `android/app/build.gradle` pulls
`com.google.firebase:firebase-analytics` directly from the Firebase BoM. iOS has
nothing: its `Podfile.lock` contains no `Firebase/Analytics`, no
`GoogleAppMeasurement`, and no `RNFBAnalytics` — only `RNFBApp`, `RNFBAuth`,
`RNFBCrashlytics`, `RNFBDatabase`, `RNFBFirestore`, `RNFBMessaging`.

`analytics_auto_collection_enabled: true` in its `firebase.json` cannot help
when the SDK is not in the binary.

Fix:

    npm install @react-native-firebase/analytics
    cd ios && pod install

Then confirm `RNFBAnalytics` and `GoogleAppMeasurement` appear in
`ios/Podfile.lock`. Until then, every iOS number in that project's Analytics is
missing, not zero — which also means any iOS conclusion drawn from it so far was
drawn from Android-only data.

### Status as of 2026-09-21 (applied, NOT yet built)

All five changes were applied to both siblings: RN 0.83.10 (+ the four
companion packages), the Firebase iOS 12.19.0 pin, Firebase Analytics,
native symbol upload, and `startup_ready` instrumentation. `Podfile.lock` in
each shows React-Core 0.83.10, fmt 12.1.0, FirebaseAuth 12.19.0,
RNFBAnalytics 23.8.8, and is in sync with `Pods/Manifest.lock`.

**Neither has been compiled.** Gradle configuration passes and the JS parses,
which catches plugin-order and syntax errors but proves nothing about a build.
Verify each with a release build before shipping.

Blox_Fruit's instrumentation is `startup_ready` only — its login path has no
isolated profile-fetch block to time, and inventing a span would have produced
a precise-looking number that means nothing.

**The Crashlytics plugin apply order had to be fixed in BOTH siblings.** Each
applied `com.google.gms.google-services` and `com.google.firebase.crashlytics`
at the *bottom* of `android/app/build.gradle`, after `android {}`. The
Crashlytics plugin registers its `firebaseCrashlytics {}` extension per build
type at apply time, so a block inside `buildTypes.release` fails configuration
with "Could not find method firebaseCrashlytics() ... on
BuildType$AgpDecorated_Decorated". Both applies must sit above `android {}`.

### Both siblings also need

- The **Firebase iOS 12.19.0 pin** (section 2) if they ship iOS — the prewarming
  logout is a Firebase SDK bug and affects any app on an older SDK.
- The **Crashlytics native symbol** setup (section 3). `Blox_Fruit` has no
  `firebaseCrashlytics` block at all, so its native crashes are undiagnosable
  for the same practical reason this app's were.

### Blox_Fruit x86_64 — a real bug, unlike here

`Blox_Fruit` excludes **both** `**/x86/**` and `**/x86_64/**` in
`packaging { jniLibs { excludes } }`. That genuinely drops the ABI, so removing
the `x86_64` exclude there is a real fix. `mm2values` already excludes only
`**/x86/**` and is correct.

Note that mm2values' build.gradle comment credits `abiFilters` for this, which
is the wrong mechanism — its `jniLibs` line is what actually works. Do not copy
that reasoning.
